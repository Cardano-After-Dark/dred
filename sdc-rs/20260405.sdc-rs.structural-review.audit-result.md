### Finding: F1 — UTF-8 chunk-boundary corruption in NDJSON parsing
**Status**: resolved
**Severity**: Objection
**Location**: In `DredListener::connect_once` (reads NDJSON stream from `/channels/listen`, decodes chunks, splits on newlines) at `sdc-rs/src/lib.rs:780-784`

**Observation**:

Streaming loop:
```rust
let text = String::from_utf8_lossy(&chunk);   // line 780
buf.push_str(&text);                           // line 781
while let Some(newline_pos) = buf.find('\n') {
    let line: String = buf.drain(..=newline_pos).collect();
    ...
}
```

`stream.next()` yields `Bytes` chunks whose boundaries are dictated by the network/reqwest, not by message boundaries. A UTF-8 codepoint (2-4 bytes) can straddle two chunks. `String::from_utf8_lossy` replaces any incomplete trailing byte sequence in chunk N with `U+FFFD`, and the leading continuation bytes of chunk N+1 are also invalid in isolation → another `U+FFFD`. The original codepoint is destroyed.

DRED treats `msg` as an opaque string (per ARCHITECTURE.md: "Server is message-opaque — relays bytes"), so payloads can and will contain non-ASCII (international text, JSON-wrapped binary encodings, emoji, encrypted-channel base64, etc.). ASCII-only tests don't catch this.

**Impact**: silent data corruption on multi-byte content.

**Proposed remediation** (initial sketch): Buffer bytes, not strings. Split on `\n` byte, then decode complete lines. Decode runs only after a complete line is assembled, so multi-byte codepoints straddling a chunk boundary are preserved intact. Invalid UTF-8 in a complete line → warn+skip, keep going.

```rust
let mut buf: Vec<u8> = Vec::new();
...
buf.extend_from_slice(&chunk);
while let Some(pos) = buf.iter().position(|&b| b == b'\n') {
    let line_bytes: Vec<u8> = buf.drain(..=pos).collect();
    let line = match std::str::from_utf8(&line_bytes) {
        Ok(s) => s.trim(),
        Err(e) => { warn!(error = %e, "invalid UTF-8 in NDJSON line, skipping"); continue; }
    };
    if line.is_empty() { continue; }
    match serde_json::from_str::<DredMessage>(line) { ... }
}
```

**Refined remediation** (server-grade, adopted): The initial sketch is correct but has avoidable costs for server-side use (replication listener). Three refinements:

1. **`BytesMut` persistent buffer, `split_to` for zero-copy framing** — `split_to(n)` is O(1) refcount-based; avoids the O(n) element shift that `Vec<u8>::drain` incurs. When the split-off prefix is dropped, BytesMut can reclaim the head region on subsequent writes (ring-buffer-like: it reuses tail space when possible; falls back to a single compacting memcpy only when it must extend past current capacity with a freed head). The `bytes` crate is already a transitive dependency via reqwest — no new dependency.

2. **`serde_json::from_slice` directly on borrowed bytes** — avoids per-message `Vec<u8>` allocation from `drain().collect()`. `from_slice` validates UTF-8 during parse (catches corrupt bytes as `serde_json::Error`). `DredMessage`'s `Option<String>` fields own their data, so the parsed message doesn't borrow from the buffer, and we can `split_to` / drop the bytes after parse. Zero intermediate copy.

3. **Bounded buffer (DoS guard)** — a stream with no newlines grows `buf` without bound. For a server-side listener handling untrusted peers this is a real DoS vector. Cap the maximum message length; exceeding it is a protocol error → disconnect, reconnect with backoff.

**Buffer sizing policy** (design decision):
- `MAX_MESSAGE_BYTES` — a per-message cap chosen to exceed legitimate DRED message size with headroom. Protocol error if exceeded. (Default: 1 MiB; configurable via builder.) Named for the domain concept (*message*); messages happen to be lines *because* the current wire framing is NDJSON/JSONL, but that is a temporary framing choice — when a framing change arrives (length-prefixed, CBOR, etc.) the cap stays meaningful as a message limit.
- **Minimum initial capacity**: at least `2 * MAX_MESSAGE_BYTES + 2 * MAX_CHUNK_BYTES` — two max-sized messages in flight plus one-or-two network packets of new arrival.
- **Ideal initial capacity**: ~10× the minimum, to absorb bursts of max-sized messages without triggering BytesMut's single-case compacting memcpy. (Default: 16 MiB; configurable via builder.)
- **Application guidance**: Applications that packetize their messages (fixed smaller frames rather than variable-length maxima) will stream far more efficiently through this buffer.

**Server-context transferability** (design note): These same sizing decisions apply — with heavier impact — to the server-side replication listener (DredReplicator / Replicant). A server fans in NDJSON streams from many peers concurrently; each stream holds its own buffer, and any single mis-sized buffer or missing DoS guard scales N-fold. The caps and defaults chosen here are the starting point for the server listener when this code (or its protocol patterns) is carried into the server context.

**Refined code**:

```rust
use bytes::BytesMut;

pub struct ListenerBufferConfig {
    pub max_message_bytes: usize,
    pub initial_capacity: usize,
}

impl Default for ListenerBufferConfig {
    fn default() -> Self {
        Self {
            max_message_bytes: 1 << 20,       // 1 MiB
            initial_capacity: 16 * (1 << 20), // 16 MiB — ~10x minimum viable
        }
    }
}

// Inside connect_once:
let cfg = &self.shared.buffer_config;
let mut buf = BytesMut::with_capacity(cfg.initial_capacity);

loop {
    tokio::select! {
        _ = self.cancel.cancelled() => return Err(DredError::Cancelled),
        _ = tokio::time::sleep_until(heartbeat_deadline) => { ... return StreamEnded },
        chunk = stream.next() => {
            let chunk = match chunk { ... };

            if buf.len() + chunk.len() > cfg.max_message_bytes * 2 {
                // Conservative: if total unparsed exceeds 2x message cap, something
                // is wrong (no terminator in a very long stretch). Disconnect.
                return Err(DredError::Protocol(format!(
                    "unparsed buffer exceeded {} bytes without message terminator",
                    cfg.max_message_bytes * 2
                )));
            }
            buf.extend_from_slice(&chunk);

            while let Some(pos) = buf.iter().position(|&b| b == b'\n') {
                if pos > cfg.max_message_bytes {
                    return Err(DredError::Protocol(format!(
                        "message exceeds {} bytes", cfg.max_message_bytes
                    )));
                }
                let line = buf.split_to(pos + 1);     // O(1) refcount split
                let trimmed = &line[..pos];
                let trimmed = if trimmed.last() == Some(&b'\r') {
                    &trimmed[..trimmed.len() - 1]
                } else { trimmed };
                if trimmed.is_empty() { continue; }

                match serde_json::from_slice::<DredMessage>(trimmed) {
                    Ok(msg) => { /* signal connected, heartbeat, dedup, route */ }
                    Err(e) => warn!(error = %e, "failed to parse NDJSON line"),
                }
                // `line` (BytesMut) drops here — refcount release, no data copy.
            }
        }
    }
}
```

**Dialog during resolution** (continued):

> **User**: "because we'll use this in a server environment, it's worth getting it right. when a message crosses the packet boundary, does it append to the buffer or make a separate buffer?"
>
> **Rusty**: Appends to the same buffer — one persistent `Vec<u8>` (or `BytesMut`) declared outside the loop. `extend_from_slice(&chunk)` mutates it in place; partial data from packet N sits in `buf`, packet N+1's bytes are appended, the split message reassembles in that single buffer.

> **User**: "if we keep extending the same buffer, does it grow unbounded? If not, why not?"
>
> **Rusty**: In normal operation, no — `buf` only holds *unparsed* bytes. Each complete line is drained/split out immediately on its `\n` terminator, so `buf.len()` stabilizes near `max(in-flight partial line) + max(single chunk)`. Capacity stabilizes at the high-water mark. In pathological cases — a stream with no newlines — it grows unbounded. That is a real DoS vector for server-side use and needs a bounded-line guard.

> **User**: "right, we can limit the message size. We should ensure the buffer can grow large enough for 2 max-sized messages, plus a network packet or maybe two. at least — but if they send max sized messages then it will be copying data to realign it with the head of the buffer (which as we discussed in a side channel, is copy-reorganized when it tries to use more of the buf-tail than is existent; like a ring buffer but with a single special-case copy behavior). I'd want the buffer to ideally be an order of magnitude larger than that minimum to be able to cope with bursts of maximum-sized messages. Arranging the applications to use packetized messages will let things stream more efficiently."
>
> **Rusty**: Captured in the buffer sizing policy above — minimum `2 × MAX_MESSAGE_BYTES + 2 × MAX_CHUNK_BYTES`, ideal ~10× minimum to avoid BytesMut's single-case compacting memcpy under bursts. Application-side packetization is orthogonal protocol guidance that reduces time spent near max-message limits.

**Resolution**: Applied server-grade remediation as described above.

Changes to `sdc-rs/src/lib.rs`:
- Added `bytes::BytesMut` import.
- New public type `ListenerBufferConfig { max_message_bytes: usize, initial_capacity: usize }` with `Default` impl (1 MiB / 16 MiB). Naming uses `message` rather than `line` because messages happen to be lines *only because* the current wire framing is NDJSON/JSONL; the cap remains meaningful under alternate framings.
- `SharedInner` and `DredClientBuilder` carry a `buffer_config: ListenerBufferConfig`. New builder method `buffer_config(config)`.
- `DredListener::connect_once` replaces `String::from_utf8_lossy` + `String::push_str` + `String::drain`-per-line with: persistent `BytesMut` buffer (initial_capacity), `extend_from_slice` on chunk arrival, DoS guard (`buf.len() + chunk.len() > 2 * max_message_bytes → DredError::Protocol + disconnect`), per-line guard (`pos > max_message_bytes → DredError::Protocol + disconnect`), `split_to(pos + 1)` for O(1) refcount framing, `serde_json::from_slice` directly on the borrowed byte slice (no intermediate allocation), CRLF tolerance.
- Parse-error log now emits `String::from_utf8_lossy(trimmed)` for diagnostic readability.

Change to `sdc-rs/Cargo.toml`:
- Added `bytes = "1"` direct dependency (already transitive via reqwest).

Added unit tests in `sdc-rs/src/lib.rs`:
- `buffer_preserves_utf8_split_across_chunks` — splits `"日本語"` mid-codepoint, verifies reassembly and correct deserialization.
- `buffer_processes_multiple_messages_in_one_chunk` — verifies the inner while-loop drains all complete lines.
- `buffer_retains_partial_tail_across_chunks` — verifies unterminated tail is preserved and reassembled with the next chunk.
- `buffer_handles_cr_lf_terminator` — tolerates CRLF.

Test results: 33 unit tests pass (29 pre-existing + 4 new), 2 doc-tests pass. Integration tests not run (require live DRED server).

Server-context transferability note: these same buffer sizing, DoS guard, and framing patterns apply directly to the server-side replication listener (DredReplicator/Replicant). A server fans in streams from N peers concurrently; every missing guard scales N-fold. When this protocol-handling code is carried into the server context, start from this configuration and tune `initial_capacity` upward based on per-peer concurrency.


**Dialog during resolution**:

> **User**: "it looks like that approach rejects any message that will hit at the network packet boundary, which seems like a DoS attack vector. is that accurate?"
>
> **Code Whisperer/Rusty**: No. The UTF-8 decode runs **after** a `\n` is found in the buffer, i.e. once a complete line is assembled. Bytes straddling a packet boundary are buffered intact — chunk N's trailing partial-codepoint bytes sit in `Vec<u8>`, chunk N+1 arrives with the continuation bytes, and only once `\n` arrives do we decode a full line. `from_utf8` on a complete NDJSON line fails only if the server itself emitted invalid UTF-8, which `serde_json` cannot do. Not a DoS vector.

> **User**: "is it possible for a binary \n to be in the data and match your scan?"
>
> **Code Whisperer/Rusty**: Yes, a 0x0A byte in the payload would match the scan — but in well-formed NDJSON from a `serde_json` serializer, 0x0A never appears inside a line. Literal newlines inside JSON string values are escaped as the two-byte sequence `\n` (0x5C 0x6E). This framing assumption is identical to the current code (`buf.find('\n')` on a `String` does the same byte-level scan). If the server were compromised/buggy and injected raw 0x0A, NDJSON framing is inherently fragile — but that's a pre-existing architectural concern, not introduced by this remediation.

### Finding: F2 — Server error bodies discarded in `ServerStatus` variant
**Status**: resolved
**Severity**: Concern
**Location**: `DredError::ServerStatus(reqwest::StatusCode)` at `sdc-rs/src/lib.rs:23`; raised in four HTTP paths — `post_message` (`src/lib.rs:522-524`), `list_channels` (`src/lib.rs:551-553`), `post_create_channel` (`src/lib.rs:615-617`), `connect_once` (`src/lib.rs:745-747`).

**Observation**:
All four HTTP error paths do `Err(DredError::ServerStatus(resp.status()))` on non-success, discarding the response **body** — which per `src/server/DredServer.ts` and ARCHITECTURE.md carries JSON error details (`{error: "..."}`). Callers get a status code but no reason. Integration tests can only assert "some error," not which. As the server evolves, new error classes all look alike to the client.

**Design refinement** (from dialog):
The library should **discriminate log-noise**: normal 4xx responses are caller-handleable business feedback and should propagate quietly (with body preserved); 5xx responses represent server-side failure and warrant a `warn!`; body-read failures warrant a `warn!`; success responses with unparseable bodies warrant a `warn!`.

**Architectural follow-up** (idempotent dispositions):
This finding surfaced an adjacent concern about idempotent operations — e.g. `create_channel` on an existing name, `joinChannel` when already a member. The question of whether these should surface as errors or be treated as success is cross-cutting (affects DredServer, TS DredClient, and sdc-rs) and an API-design decision, not a structural fix. Logged as an architecture open question (ARCH-dspn7k3qja) in `sdc-rs/sdc.arch.jsonl` with guidance to add an opt-in disposition flag on mutating operations. F2's fix here unlocks caller-side body inspection, which is a prerequisite for any disposition handling.

**Proposed remediation**:
1. Change `DredError::ServerStatus(StatusCode)` to `ServerStatus { status: StatusCode, body: String }`.
2. Add private helper `check_status(resp) -> Result<Response, DredError>` — reads body on non-success, warns on 5xx, silent on 4xx, warns on body-read failure.
3. Update `Display` to include body when non-empty.
4. Update all 4 call sites to `check_status(resp).await?` before `.json()`.
5. Add `warn!` at the 3 response-body-JSON-parse-failure sites (success status + malformed body = weird).

**Resolution**: Applied as specified.

Changes to `sdc-rs/src/lib.rs`:
- `DredError::ServerStatus(StatusCode)` → `ServerStatus { status: StatusCode, body: String }`.
- Added private `check_status(resp) -> Result<Response, DredError>` helper. On non-success: reads body (best effort), warns on 5xx (server-side failure = noteworthy), stays quiet on 4xx (caller-handleable). Warns when body read itself fails.
- Updated `Display` to include body when non-empty.
- All 4 HTTP call sites (`post_message`, `list_channels`, `post_create_channel`, `connect_once`) replaced the inline `if !status().is_success() { ... }` pattern with `check_status(resp).await?`.
- Added `warn!` at the 3 response-body-JSON-parse-failure sites (success status + malformed body).
- Added 2 test assertions in `error_display` covering the new variant with empty and non-empty body.

Test results: 33/33 unit tests pass; 2/2 doc-tests pass; clippy clean on lib.

Architectural follow-up captured in `sdc-rs/sdc.arch.jsonl` and `sdc-rs/sdc.arch.md` Open Questions → **ARCH-dspn7k3qja** (idempotent operation dispositions; guidance: opt-in disposition flag on mutating APIs, default strict).

### Finding: F3 — `DredError::Protocol` overloaded across unlike failure modes
**Status**: resolved
**Severity**: Concern
**Location**: `DredError::Protocol(String)` raised at many sites across `sdc-rs/src/lib.rs`:
- Identity b64/length validation: lines 263, 266, 270, 273
- API usage rejection (`create_channel` called with `encrypted: true`): line 653
- `update_channels` connection-setup failure: lines 1128, 1137
- NDJSON stream body-parse failures (response-body JSON parses from F2): lines 608, 638, 703
- Buffer DoS guards (new in F1): lines 864, 873

**Observation**: `DredError::Protocol(String)` is used as a catch-all for *at least four distinct categories* of failure:
1. **Input validation** — caller passed bad bytes (wrong-length keys, invalid base64). Caller-fixable before any network activity.
2. **API misuse** — caller called the wrong entry point (e.g. `create_channel(encrypted=true)` → "use create_encrypted_channel"). Not a wire-protocol error.
3. **Connection-setup timeout** — `update_channels` could not establish a new listener within `connect_timeout`. A time/infrastructure failure, not a protocol violation.
4. **Actual protocol violation** — server emitted malformed JSON, wrong-length payloads, or sent messages without terminators (DoS guard).

A caller matching on `DredError` can distinguish `Transport`, `ServerStatus`, `StreamEnded`, `Cancelled`, but everything else dumps into `Protocol`. "new connection not established within 200ms" has nothing to do with protocol compliance — it's a local timeout. Callers that want to retry on timeout but give up on true protocol errors cannot currently tell them apart.

Impact: loss of actionable error discrimination; callers either match the `String` payload (fragile) or treat all `Protocol` errors the same (wrong).

**Proposed remediation**: Split `DredError::Protocol` into categories:
```rust
pub enum DredError {
    Transport(reqwest::Error),
    ServerStatus { status, body },
    /// Caller-supplied bytes failed validation (wrong length, invalid base64, etc.).
    InvalidInput(String),
    /// Caller called the wrong API entry point for the state.
    ApiUsage(String),
    /// A bounded wait elapsed (connection setup, rotation handoff).
    Timeout(String),
    /// Server emitted data violating the wire protocol.
    Protocol(String),
    StreamEnded,
    Cancelled,
}
```
Update each raising site to the appropriate variant. Update `Display` for the new variants. This is API-breaking at the `DredError` level — any external caller matching on variants will need to update.

**Scope note**: this is closer to a small refactor than a pointed fix; touches ~10 raise sites and reshapes the public error surface. Worth verifying the user wants it before applying.

**Resolution**: Applied as specified.

Changes to `sdc-rs/src/lib.rs`:
- Extended `DredError` enum with three new variants after `ServerStatus`:
  - `InvalidInput(String)` — caller-supplied bytes failed validation (raised pre-network).
  - `ApiUsage(String)` — caller called wrong API entry point.
  - `Timeout(String)` — bounded wait elapsed (connection setup, rotation handoff).
  Each variant carries doc comments describing its category.
- `Display` impl extended with arms for the three new variants: `"invalid input: ..."`, `"api usage error: ..."`, `"timeout: ..."`.
- Reclassified raise sites:
  - `Identity::from_base64` — 4 raises (b64 decode failures and length checks) → `InvalidInput`.
  - `DredClient::create_channel` — the `encrypted: true` guard → `ApiUsage`.
  - `DredSubscription::update_channels` — both the "new listener exited" and "not established within timeout" raises → `Timeout`.
- Unchanged as `Protocol`: three `.json().await` parse-failure wraps in `post_message`/`list_channels`/`post_create_channel` (server sent success but malformed body) and both DoS guards in `connect_once` (oversized/unterminated stream messages). These are genuine wire-protocol violations.
- Extended `error_display` test with assertions for each new variant's `Display` output.

Test results: 33/33 unit tests pass; 2/2 doc-tests pass; clippy clean on lib.

Drive-by fix: pre-existing typo in `ServerStatus` doc comment (`/ response` → `/// response`) corrected; was adjacent to the variant block being edited.

**API breaking**: yes — external callers matching on `DredError::Protocol(_)` for the reclassified cases must add arms for `InvalidInput`, `ApiUsage`, `Timeout`. No external callers known (crate private).

### Finding: F4 — HTTP request scaffolding duplicated across call sites
**Status**: resolved
**Severity**: Concern
**Location**: Four HTTP methods on `DredClient`/`DredListener` at `sdc-rs/src/lib.rs`:
- `DredClient::post_message` (~lines 502-532)
- `DredClient::list_channels` (~lines 570-596)
- `DredClient::post_create_channel` (~lines 680-712)
- `DredListener::connect_once` (~lines 737-760 for request build)

**Observation**: After F2 extracted `check_status`, each HTTP method still independently does:
```rust
let resp = self.inner.http
    .post(format!("{}/path/{}", self.inner.base_url, ...))
    .header("content-type", "application/json")
    .header("accept", "application/json")
    .header("clientid", &self.inner.client_id)
    .json(&body)
    .send()
    .await?;
let resp = check_status(resp).await?;
let result: T = resp.json().await.map_err(|e| { warn!(...); DredError::Protocol(...) })?;
```

The repeated parts are: URL composition, three standard headers, body serialization, send, status check, JSON decode with warn+wrap. Four instances. Any protocol-header change (e.g. adding auth, API version) requires touching four call sites.

**Proposed remediation**: Consolidate into one generic round-tripper on `DredClient`:
```rust
async fn send_json<B, R>(&self, method: Method, path: &str, body: Option<&B>) -> Result<R, DredError>
where B: Serialize + ?Sized, R: DeserializeOwned,
{
    let mut req = self.inner.http.request(method, format!("{}/{}", self.inner.base_url, path))
        .header("content-type", "application/json")
        .header("accept", "application/json")
        .header("clientid", &self.inner.client_id);
    if let Some(b) = body { req = req.json(b); }
    let resp = check_status(req.send().await?).await?;
    resp.json().await.map_err(|e| {
        warn!(error = %e, "invalid response json");
        DredError::Protocol(format!("invalid response json: {e}"))
    })
}
```
Each public method becomes one line. `connect_once`'s request-build path is the odd one out (it consumes the response as a stream, not as JSON) and stays separate.

**Scope note**: dependent on / best sequenced with F3 (error categorization) — the `Protocol`/`InvalidInput` split affects the fallback variant in `send_json`.

**Resolution**: Applied as two private helpers on `DredClient`:

- `get_json<R: DeserializeOwned>(path) -> Result<R, DredError>` — GET with `accept` + `clientid` headers, `check_status`, JSON parse with `warn!` + `Protocol` wrap.
- `post_json<B: Serialize + ?Sized, R: DeserializeOwned>(path, body) -> Result<R, DredError>` — POST with `content-type` + `accept` + `clientid` headers, same status/parse handling.

Refactored call sites:
- `post_message` → `self.post_json(&format!("/channel/{channel}/message"), &body).await`
- `list_channels` → `self.get_json("/channels").await` (wrapper struct stays for `.channels` extraction)
- `post_create_channel` → `self.post_json(&format!("/channel/{name}"), options).await`
- `connect_once` intentionally stays separate — it consumes the response as a byte stream, not JSON.

`DeserializeOwned` import added. Net change: 50 insertions, 62 deletions (-12 lines). Error messages now include the path for diagnostic context.

Standardization effect: `list_channels` now sends `accept: application/json` (previously omitted); all HTTP methods use identical header sets via the helpers. Future protocol-header changes (auth, API version) touch exactly one place.

Test results: 33/33 unit tests pass; integration tests compile; clippy clean.

### Finding: F5 — `DredListener::connect_once` fuses transport, framing, protocol, and routing
**Status**: resolved
**Severity**: Concern
**Location**: `DredListener::connect_once` (single async method handling the entire streaming loop) at `sdc-rs/src/lib.rs:754-914` (~160 lines after F1).

**Observation**: A single async method owns all of: HTTP request construction, response validation, streaming byte accumulation (BytesMut buffer from F1), DoS guard, line framing, UTF-8 decoding, JSON parsing, heartbeat state machine, dedup check, and per-channel routing. There are no seams at which a unit test can validate one concern independently of the others. The protocol logic — heartbeat interpretation, heartbeat-deadline computation, dedup gating, channel routing — is knowable and testable as pure functions over `DredMessage`, but is currently only exercised end-to-end via integration tests against a live server.

The F1 fix introduced a testable `drain_messages` helper in the test module. That demonstrates the shape: extracting the pure per-message logic into a function over `(message, state) -> action` would let the heartbeat interval negotiation, dedup decision, and routing dispatch be unit-tested directly.

Impact: protocol logic can only be validated at full integration; evolving the heartbeat protocol or dedup semantics requires re-deriving confidence via a live server each time.

**Proposed remediation**: Extract the per-message handler into a pure (or near-pure) async fn:
```rust
enum HandleAction { Continue, ConnectedFirst, Heartbeat(Duration), Dedup, Route, NoRoute }
fn handle_message(msg: &DredMessage, dedup: &Deduplicator, senders: &HashMap<_,_>) -> HandleAction { ... }
```
Leave the transport/IO loop in `connect_once`. Unit-test `handle_message` with synthetic messages covering: heartbeat-info with/without interval, heartbeat, ocid-dedup hit/miss, channel-routed, channel-missing. The goal is not to split for its own sake but to make protocol semantics testable at a smaller grain.

**Scope note**: moderate refactor; affects the inner loop of `connect_once` only; no public API change.

**Resolution**: Extracted `MessageAction` enum and `classify_message` pure function. `connect_once` now calls `classify_message(msg, dedup, senders)` and matches on the returned action to apply I/O side effects (heartbeat state updates, sender sends, logging). 7 new unit tests covering: heartbeat-info with interval, heartbeat-info without interval (fallback to reset), heartbeat reset, duplicate ocid, routable channel, unroutable channel, no-ocid message. All 40 unit tests pass.

### Finding: F6 — Dead public API surface: `DredListener` and its methods
**Status**: resolved
**Severity**: Concern

### Finding: F7 — `CreateChannelOptions` permits invalid state combinations
**Status**: resolved
**Severity**: Suggestion
**Location**: `CreateChannelOptions` struct at `sdc-rs/src/lib.rs:691-720`.

**Observation**: The struct's fields are coupled in the protocol but decoupled in the type:
- `encrypted: bool` — whether the channel is encrypted.
- `owner: Option<String>` — base64 pubkey of owner, only meaningful when `encrypted=true`.
- `signature: Option<String>` — signed channel-name, only meaningful when `encrypted=true`.
- `members: Vec<String>` — initial members, required (per doc) if `allow_joining` is not true.

A caller can construct `CreateChannelOptions { encrypted: true, owner: None, signature: None, ... }` directly, or `CreateChannelOptions { encrypted: false, owner: Some("..."), signature: Some("..."), ... }`, both type-valid, both protocol-nonsense. The runtime guard is `create_channel` rejecting `encrypted=true` ("use create_encrypted_channel") — but that only covers one misuse. Nothing prevents passing bogus `owner`/`signature` on a plaintext channel (the server ignores them, no feedback); nothing catches forgetting `members` with `allow_joining != Some(true)`.

This is a Rust-idiomatic "parse, don't validate" opportunity. Under Rust's type system, the encrypted/plaintext distinction could be encoded in the type, making invalid states unrepresentable.

**Proposed remediation** (two options, author's pick):

**Option A** — sum type over options:
```rust
pub enum CreateChannelOptions {
    Plaintext {
        allow_joining: Option<bool>,
        member_limit: Option<u32>,
        expires_at: Option<String>,
        message_lifetime: Option<u64>,
        members: Vec<String>,
    },
    // owner + signature are set by create_encrypted_channel, not the caller,
    // so Encrypted carries only the caller-supplied fields:
    Encrypted {
        allow_joining: Option<bool>,
        member_limit: Option<u32>,
        expires_at: Option<String>,
        message_lifetime: Option<u64>,
        members: Vec<String>,
    },
}
```
`create_channel` takes `CreateChannelOptions::Plaintext`, `create_encrypted_channel` takes `CreateChannelOptions::Encrypted` (or just the inner struct fields, since Encrypted has no Plaintext-distinct fields yet).

**Option B** — separate structs, serde handles both:
```rust
pub struct CreateChannelOptions { /* allow_joining, member_limit, expires_at, message_lifetime, members */ }
// encrypted/owner/signature are set by the client code, never the caller.
```
Simpler. The `encrypted: bool` in the struct disappears; the serialization form is chosen by whichever method is called.

Option B is lower-churn and more aligned with the current API (existing callers keep their option structs). Option A is more explicit about state.

**Scope note**: API-breaking change to `CreateChannelOptions`; every caller of `create_channel`/`create_encrypted_channel` touches. Not urgent — current runtime guard is adequate for single-writer.

**Resolution**: Applied **Option B** — removed `encrypted`, `owner`, `signature` from `CreateChannelOptions`. Added internal `CreateChannelWireBody<'a>` that `#[serde(flatten)]`s the caller's options and adds protocol fields. `create_channel` sends wire body with `encrypted: None`; `create_encrypted_channel` fills `encrypted: Some(true)`, `owner`, `signature` from the `Identity`. Removed `DredError::ApiUsage` variant (sole producer was the now-unnecessary runtime guard). Updated integration tests: removed obsolete `create_channel_rejects_encrypted_opts_without_identity` test; refactored `create_encrypted_channel_rejects_bad_signature` to use raw `serde_json::json!` body. All 57 tests pass.

### Finding: F8 — `Deduplicator::check` return-value polarity ambiguous
**Status**: resolved
**Severity**: Suggestion
**Location**: `Deduplicator::check` at `sdc-rs/src/lib.rs:141-149`.

**Observation**: `check(&self, ocid: &str) -> bool` — returns `true` if the ocid is *new*, `false` if it's a *duplicate*. Every call site comments or names the result to disambiguate:
```rust
// at post_message (pre-register echo suppression)
self.inner.dedup.check(&ocid);  // side-effect only; bool discarded

// at connect_once (stream dedup gate)
if !self.shared.dedup.check(ocid) {
    debug!(ocid, "duplicate, skipping");
    continue;
}
```
The name `check` gives no signal about which boolean means which outcome. A reader has to consult the doc. The polarity is also the opposite of many "is this a dup?" idioms (where `true` would mean "yes, duplicate"). The doc comment says "Returns true if this ocid is new (not a duplicate)" — necessary because the name doesn't convey it.

**Proposed remediation** — rename to reflect polarity explicitly. Options:
- `is_new(&self, ocid: &str) -> bool` — true = new.
- `check_and_mark(&self, ocid: &str) -> bool` — signals the side effect (inserts if new).
- `try_mark_seen(&self, ocid: &str) -> bool` — true = was not previously seen (now marked).

`is_new` is clearest at the call site:
```rust
if !self.shared.dedup.is_new(ocid) {
    debug!(ocid, "duplicate, skipping");
    continue;
}
```
Reads as "if not new, skip."

**Resolution**: Renamed `check` → `is_new` across all 18 call sites (lib.rs only; no integration test references). Added "Inserts the ocid into the current generation as a side effect" to the doc comment. All 57 tests pass.

**Scope note**: API-breaking rename. Trivial to apply — search-and-replace across the crate. No external callers known (crate is private).

### Finding: F10 — `unreachable!()` on `Ok(())` in `DredListener::run` is fragile
**Status**: resolved
**Severity**: Suggestion
**Location**: `DredListener::run` at `sdc-rs/src/lib.rs` — the `match self.connect_once().await` arm for `Ok(())`.

**Observation**: `connect_once` is designed to loop forever and return only on error (`Cancelled`, `StreamEnded`, `Transport`, etc.). The `run` loop relies on this and writes `Ok(()) => unreachable!()`. If a future refactor of `connect_once` introduces a path that returns `Ok(())` for normal stream closure, or on protocol shutdown, the listener panics instead of reconnecting gracefully. This is a fragile contract encoded only in the panic.

**Proposed remediation** — two clean options:
1. **Change `connect_once`'s return type** to `Result<Infallible, DredError>` (a.k.a. `std::convert::Infallible`, or equivalently `!` once stabilized). The type system then forbids returning `Ok`. `run`'s match can use `match ... { Err(e) => ... }` without the unreachable arm.
2. **Treat `Ok(())` as `StreamEnded`** — if it ever happens, reconnect like any other clean end-of-stream. Removes the panic, costs nothing.

Option 1 is the stronger encoding. Option 2 is the minimal change.

**Scope note**: trivial.

**Resolution**: Applied Option 1 — changed `connect_once` return type to `Result<std::convert::Infallible, DredError>`. In `run`, replaced `match self.connect_once().await { ... Ok(()) => unreachable!() }` with `let Err(e) = self.connect_once().await;` — the `Ok` variant is uninhabited so only `Err` is reachable. The type system now enforces the invariant; a future refactor that tries to return `Ok` from `connect_once` will get a compile error. All 57 tests pass.
